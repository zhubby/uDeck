# 应用启动与状态更新优化

本次保留 Python + QML，完成轻量转发、按需页面、列表模型和后台保存。CM4 隔离对照中，五个非终端应用的直接 D-Bus 激活 P95 均低于 250 ms，最慢一组为 207 ms；阅读器书架首帧从 3.31 秒降到 2.92 秒，PSS 从 187 MiB 降到 115 MiB。其他应用首次启动没有普遍改善。1,231 项 Linux ARM64 回归全部通过，物理按键、真实中文输入和当前安装桌面的完整验收仍需人工完成。

## 实现

| 路径 | 当前行为 | 验证 |
| --- | --- | --- |
| 桌面再次进入应用 | 对原生应用直接异步调用会话 D-Bus `Open`；没有实例时才通过 desktop entry 启动 | 独立 dbus-next 服务验证 Qt 桌面客户端，涵盖成功、拒绝和实例不存在 |
| 外部命令启动 | 轻量入口先解析原有参数并转发，再按需加载 GUI、音视频和 WebEngine | 使用不存在的 Qt 平台插件运行转发测试，仍能成功转发；覆盖终端参数、诊断、启动竞态、超时和拒绝 |
| 内容页面 | 阅读器、音乐、视频和模拟器首次进入内容时创建，返回列表后保留实例；浏览器同步创建首屏 | 真实 PDF/TXT 首次打开与保留实例；PDF 恢复滚动位置；真实浏览器首次导航 |
| 资源列表 | `QAbstractListModel` 按需提供卡片；选中索引、选中项独立通知；普通 UI JSON 不再包含完整资源列表 | 1 万条资源选中操作不重建集合、不 reset 模型；重复队列条目保持原来的首次匹配行为 |
| 应用保存 | 单个后台线程串行合并写入；资源索引独立保存；关闭时等待最后一次写入 | 阻塞 `fsync`、最终状态、索引不重复写入、序列化失败、错误通知、迁移失败重试和损坏文件恢复 |
| 启动诊断 | 增加进程起点、运行时导入、Qt、控制器、QML、首帧、资源扫描完成和激活代次时间 | 原有 `Diagnose` 字段保留，新增 `performance`；独立 D-Bus 客户端读取 |

实现入口见 [应用启动器](../../src/udeck/apps/main.py)、[桌面启动控制](../../src/udeck/launch_controller.py)、[资源模型](../../src/udeck/apps/common/model.py)、[后台保存](../../src/udeck/apps/common/state.py)。原有命令、桌面 ID、D-Bus 方法和终端会话参数保留。

界面仍通过一个小型 JSON 传递菜单、播放进度等状态；完整诊断快照保留资源列表。列表变更或扫描完成时仍需构造集合，索引快照只在集合变更时复制。按需创建把内容引擎的首次初始化推迟到第一次打开内容，不能消除解码、WebEngine 或游戏本身的成本。

## 数据兼容与恢复

原有 `<app>.json` 中的内嵌 `index` 可直接读取。保存时先原子写入 `<app>.index.json`，再原子写入带固定 `indexFile` 文件名的运行状态。播放位置、来源、收藏、队列及偏好保留原字段。运行状态替换失败时，旧文件仍然可读，后续保存可重试。

索引是可重新扫描得到的缓存，两个文件分别原子替换，不提供跨文件事务。仅播放位置变化不会重写索引。损坏输入在首次成功保存前保留为 `.recovery.json`；索引损坏不清空播放位置。正常退出等待最后一次保存，写入失败通过 Qt 主线程显示错误。

旧版本不会读取分离的索引，回退后会从保留的来源重新扫描；播放位置等运行状态仍兼容。需要完整恢复时，退出相关应用后恢复升级前的应用数据目录。此次实机探测没有安装新包，也没有修改用户的运行会话、默认终端或应用数据。

## 验证与计时口径

Linux ARM64 在 Debian 13、Qt 6.8.2 下完成 84 个模块、1,231 项测试，零失败、零跳过；按发布流程在同一 pytest 进程中再运行也全部通过（约 363 秒）。启用必须存在的原生 QMLTermWidget 插件；真实引擎、终端 PTY、会话生命周期、主题、中英文、窗口/输入路由和独立 D-Bus 测试均在范围内。[逐模块汇总](evidence/app-performance-2026-11-10/validation.json)、[同进程汇总](evidence/app-performance-2026-11-10/validation-combined.json) 和 [JUnit](evidence/app-performance-2026-11-10/linux-validation-combined.xml) 保留结果。13 条警告来自 dbus-next 在 Python 3.13 下使用的废弃装饰器。

wheel 和 arm64 Debian 包均已构建；构建本身使用 `DEB_BUILD_OPTIONS=nocheck`，测试由上述独立步骤完成，没有发布新版本。Debian 构建镜像只含构建依赖，因此仅解包验证，未完成整个桌面运行依赖的安装配置；[解包验证](evidence/app-performance-2026-11-10/package-verification.json) 确认运行时、模型、IPC 和 QML 文件与源码一致，并在不可用的 Qt 平台下检查已打包的阅读器/终端诊断入口。

对照基线为 `1f26587a9449ccdc0714ddafb9605193c5143677`，只加入 [计时补丁](evidence/app-performance-2026-11-10/baseline-instrumentation.patch) 和同一份 `performance.py`。基线保留全量 JSON、提前创建内容和同步写盘。计时工具自动创建私有 D-Bus，会话配置、数据和缓存使用独立目录，只关闭它自己启动的进程组。

性能采样均使用 `--windowed --no-input`，保留真实 Qt 渲染和应用 IPC，不打开 evdev 与物理控制器路由。表中的首帧不是带硬件输入初始化、全屏切换和用户完整配置的生产启动时间。

Linux 对照采用 ARM64 虚拟机、Xvfb/Openbox、Qt Quick Software，空应用数据，系统文件缓存保留。每个应用启动新进程 3 次，每个进程重复进入 20 次。音乐、视频、阅读器、浏览器、模拟器每次先最小化再进入；终端测已有可见窗口的重复请求，另由会话测试验证没有增加 PTY。首次启动数据是进程启动到 Qt 首帧，不是重启后的冷缓存或网页/媒体内容全部就绪。

计时同时报告外部启动器完成、请求到 Qt 窗口激活、请求到下一次 `frameSwapped`。没有新的绘制或无法取得焦点时保留缺失样本，不把方法返回时间当作窗口激活。隔离 Weston 的 Wayland 焦点请求未获准，因此该次尝试没有作为性能验收数据。

## CM4 当前证据与待验收

[初始快照](evidence/app-performance-2026-11-10/cm4-initial-snapshot.json) 来自 `clockworkpi`、aarch64、Python 3.13.5、uDeck 0.2.3：内存约 3.7 GiB，可用约 1.4 GiB，swap 已使用约 1.7 GiB。书架上的阅读器仍有 4 个 WebEngine 子进程。实际资源为音乐 0、视频 0、阅读器 1、模拟器 3，所以大库基准只说明规模瓶颈，不能认定它是当前设备卡顿的根因。swap 占用也不能单独证明正在频繁换页。

CM4 对照使用原有 Wayland/labwc、OpenGL 后端，以及设备 Python/Qt 和原生终端插件。另在同一环境用最小 Qt Quick 窗口确认了 Broadcom V3D 4.2.14.0、OpenGL 3.1、Mesa 25.0.7 的硬件驱动和 threaded render loop，[探测日志](evidence/app-performance-2026-11-10/cm4-graphics.json) 不代表持续播放的实际帧率。基线与优化源码分别放在 `/tmp`，应用状态和 D-Bus 独立；默认来源仍可能读取设备的 `~/Music`、`~/Video`、`~/Books` 和 `~/Games`，扫描结果只写到本次测试目录。未安装新包，未关闭或重用已有应用。登录信息未写入仓库或证据文件。

私有总线没有真实桌面的 `ActivateNativeApp` 服务，直接 `requestActivate()` 会受到 Wayland 焦点限制。计时使用测试专用激活桥，复用现有 `WindowService` 协议。两个版本仅在测试副本的窗口标题中追加同一个随机标记；激活桥排除启动前全部已有窗口，要求 app ID 和标记同时匹配，且只有唯一匹配才激活。预存窗口、未标记窗口和重复匹配均有拒绝测试。桥和被测应用位于同一私有总线，保留真实 compositor；这不是当前安装桌面进程的端到端按键测试。

每个版本、每个应用均启动 3 个新进程，每个进程重复外部入口 20 次；五个非终端应用另各执行 20 次独立 `gdbus Open`。表中首帧与 PSS 为三次中位数；P95 为各轮 P95 中的最大值，合计每个应用有 60 次激活样本，未计算合并 P95。终端的窗口已可见，仅测外部入口转发。

| 应用 | 首帧，基线 → 优化 | 外部入口到激活 P95，基线 → 优化 | 直接 D-Bus 到激活 P95，优化 | PSS，基线 → 优化 |
| --- | ---: | ---: | ---: | ---: |
| 音乐 | 2.467 → 2.630 s | 993 → 509 ms | 89 ms | 90.5 → 96.5 MiB |
| 视频 | 2.528 → 2.680 s | 993 → 515 ms | 70 ms | 89.5 → 96.6 MiB |
| 阅读器 | 3.307 → 2.917 s | 1,152 → 519 ms | 80 ms | 187.4 → 114.9 MiB |
| 浏览器 | 3.320 → 3.368 s | 1,155 → 517 ms | 88 ms | 186.1 → 192.0 MiB |
| 游戏 | 3.222 → 3.552 s | 1,419 → 797 ms | 207 ms | 101.7 → 107.0 MiB |
| 终端（窗口已可见） | 2.703 → 2.991 s | 958 → 446 ms | 未测 | 110.7 → 115.1 MiB |

五个应用的直接激活路径在这组隔离样本中达到 ≤250 ms 的初始目标；桌面的实现使用常驻 Qt 客户端异步调用同一 `Open` 方法，独立 `gdbus` 客户端另有自身启动成本。功能测试已覆盖真实桌面启动控制代码，但本组时间没有包含当前安装桌面的按键分发、菜单状态写入和合成器最终显示时间。外部 Python 命令入口仍比直接调用慢，不能把约 0.5–0.8 秒说成已经达到 250 ms。

优化版本五个非终端应用均取得 60/60 个激活样本；外部入口与直接请求的新 `frameSwapped` 样本分别均为 0、0、0、0、2。采样在激活后约 50 ms 收尾，整个轮询最长约 500 ms，之后的帧不纳入；已有场景也可能复用缓冲。因此本组不能给出这些路径的完整重绘 P95，也不能据窗口激活推断持续播放帧率。终端两版各取得 60 个外部入口激活和绘制样本；这是可见窗口场景，未验证最小化恢复。

阅读器的书架首帧在本组约减少 12%，PSS 约减少 39%；首次内容初始化被推迟到第一次打开文档。音乐、视频、浏览器、游戏和终端的首帧在本组均未改善，其他应用 PSS 增加约 4–7 MiB。这些结果不支持宣称所有首次启动或所有运行时卡顿已经解决。

连接恢复后的基线起点可用内存约 2.6 GiB、swap 尚未使用，与上面的初始快照不同，**没有重现初始高 swap 占用的状态**。各次首帧后只采样约 2 秒，可能包含后台扫描；这些短样本未观察到换页，但整段基线的系统计数增加了 16,502 页换出，优化段为 0。系统级变化也包括其他进程，不能全部归因于本次优化。采样结束温度约 38.9℃、`get_throttled=0x0`，原有桌面、阅读器和游戏进程均保留；没有剩余测试进程。

[原始基线](evidence/app-performance-2026-11-10/cm4-baseline.json)、[原始优化结果](evidence/app-performance-2026-11-10/cm4-optimized.json)、[比较汇总](evidence/app-performance-2026-11-10/cm4-comparison.json) 和 [运行状态](evidence/app-performance-2026-11-10/cm4-run-status.json) 保留全部样本与计数。[设备元数据](evidence/app-performance-2026-11-10/cm4-metadata.json) 确认两版扫描的实际资源数相同：音乐 0、视频 0、阅读器 1、游戏 3。[应用源码与字体哈希](evidence/app-performance-2026-11-10/cm4-source-manifests.json) 已与本地逐项匹配，仅追加 [窗口标题计时补丁](evidence/app-performance-2026-11-10/cm4-window-instrumentation.patch)；测试字体复用设备已安装的相同文件。36 份应用日志未匹配到 Python traceback、QML ReferenceError、TypeError 或 binding loop，[检查记录](evidence/app-performance-2026-11-10/cm4-verification.json) 保留范围；测试文件在取回证据后已从设备清理。

首次内容就绪、持续播放的帧时间和存储延迟尚未在 CM4 上完整采集。还需人工确认安装后桌面进入的窗口焦点、方向键、ABXY/L/R、终端原有会话、中文 IME 和原桌面恢复。自动化结果不替代这些验收；终端本组明确只测已可见窗口的重复请求。

## 复测后的 C++ 范围

本轮保留 Python + QML。再次进入可通过常驻桌面的直接 IPC 消除重复初始化，资源更新可通过模型和小状态避免整库传输，保存可转移到串行后台线程。这些收益已经能用同一语言实现。

外部命令入口仍需启动 Python 和导入 IPC 客户端，在 CM4 上多数约半秒，游戏约 0.8 秒；如果外部命令也必须达到 250 ms，可以单独评估一个原生轻量启动器。首次启动需要继续按应用分析模块导入、引擎初始化和渲染；本轮并没有证明全量改写 C++ 的收益足以覆盖迁移成本。

## 复测命令

在目标 Linux 的图形会话中，从测试源码目录执行，输出目录必须为空：

```sh
PYTHONPATH=src python3 tools/measure-applications.py \
  --output /tmp/udeck-app-performance-new \
  --cold-runs 3 --repeats 20 --sample-seconds 60
```

工具会创建私有 D-Bus，保留已有 compositor 环境。Wayland 的窗口激活可能需要桌面提供激活权限；若 `warmLauncherToActive` 样本不足，应记录为未取得验收结果，结合实际桌面启动路径继续测试。`--warm-mode visible` 可单独测量已有可见窗口的转发成本。

需要私有 Wayland 激活桥时，仅在测试源码副本的应用与终端标题中追加唯一 `udeck-perf-` 标记，再传入相同的 `--wayland-window-token`。桥拒绝与已有桌面服务共用总线，并且不会按 app ID 操作用户已有窗口。不要把测试标题补丁应用到安装版本。

```sh
PYTHONPATH=src python3 tools/benchmark-app-state.py --items 100 1000 10000 --samples 100
```

该基准使用合成元数据，不包含 QML 解析、绘制和真实存储；用于确认每次选中变化的 Python 工作量是否继续随资源量增长。要重建基线，导出上述基线提交的源码和 packaging，应用计时补丁，并复制当前 `src/udeck/performance.py`；随后使用同一 Python、Qt、采样工具和环境运行对照。

## 部署后的检查

上线后先观察一个完整启动周期及至少 60 秒音乐/视频播放：`Diagnose` 的 `qmlErrors` 应为空，激活代次应递增，保存错误不应出现；重复进入不应产生第二个主应用进程。检查 `fsync` 延迟、进程树 PSS、CPU、I/O wait 和实际换页差值，并确认退出后播放位置恢复。

发生焦点/输入错路、重复实例、保存错误或已有状态无法恢复时，恢复前一软件包；需要时恢复备份的数据目录。人工输入、真实内容播放和当前安装桌面进程的检查仍是部署后的验收项目。
